# 逐筆工單怎麼用（給 AGY 與 Lead）

> 這一份是 `worklist.md` 的說明；工單本身由 `scratch/build-worklist.mjs` 產生，
> **不要手改**——改了下次重跑就消失，而且會製造第二個真相。

## 1. 它是什麼

`worklist.md`／`worklist.json` 把「這整份計劃要做的每一筆」攤成一張表：

| 欄位 | 意思 |
|---|---|
| 狀態 | `✓` 已完成（有驗收報告）／`☐` 待做 |
| id | `quirk:…`／`heroic:…`／`class:職業:技能名`／`system:…` |
| 群 | `G1–G6`（英雄）、`C1–C8`（職業）、`Q1/Q2/Q4`（金手指）、`W6`（系統） |
| 要做什麼 | **這一筆**的下一步（不是泛用口號；依資料裡已有的控件形狀推導） |
| 驗收 | 做完要長出什麼、要怎麼證明 |

## 2. 為什麼要有它（不是多一份文件）

2026-11-05 的 W3 驗收發現：【升級】的資料與邏輯都寫好了、23 條測試全綠，
**但跑團卡上什麼都沒有**——因為沒有任何地方掛面板。那不是「漏寫程式」，
是「沒有人問過這一筆到底做完了沒」。工單就是用來回答那一題的：

- 每一筆都有 `☐`／`✓`，所以「還沒輪到」與「漏做」分得開。
- `tests/planWorklist.test.mjs` 會比對**附錄有幾筆／工單有幾筆**（35＋22＋28＋1），
  漏抄一筆就紅；也會反過來檢查工單上的 id 真的存在於 `effectFlows.json`。
- `W2` 那 16 筆還會被交叉核對「資料裡真的有多顆控件」——工單說做完、資料卻沒有，會紅。

## 3. 施工方式

1. 讀 `README.md` §0 的波次表，找出你這一波。
2. 打開 `worklist.md` 找那一節，**照列由上往下做**（每列就是一個可獨立驗收的單位）。
3. 做完一筆：跑 `npm test`＋`npm run build`，寫進回報，然後**把工單那一列改 `✓`**——
   但工單是產生的，所以正確做法是：把「這一筆做完」的事實寫進**回報**，
   由 Lead 更新產生器裡的判定條件（例如「有 spec 且面板已掛載」）後重跑。
4. 不要在工單裡手動改 `☐` → `✓`。判定條件寫在 `scratch/build-worklist.mjs`，
   這樣「做完」才有可檢查的定義（目前是：W1＝有 spec、W2＝多控件、W3＝【升級】）。

## 4. 目前的進度（每次重跑產生，不要手寫死在文件裡）

看 `worklist.md` 的表頭「（N 筆）」與每節的 ✓ 數量。重建：

```
npm run build:worklist   # 重跑產生器（改判定條件後才需要）
npm run test:planworklist
```
