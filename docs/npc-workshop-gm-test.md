# NPC 工坊 GM 實測手冊（新手 GM 視角）

> **這份文件是「測試計畫 ＋ 缺陷帳本 ＋ 逐階段紀錄」三合一。**
> 目的不是證明程式能跑（那有 `npm test`），而是回答一個測試跑不出來的問題：
> **一個只讀過規則書、沒讀過原始碼的新手 GM，實際開一張 NPC 卡時會卡在哪裡。**
>
> 執行者：DSH。被測對象：`src/features/npc-workshop/`（`NPCWorkshop.jsx` 4,242 行 ＋ 8 個資料模組 ＋ 8 個子元件）。
> 狀態一律以本檔 §7 的階段紀錄為準；數字會腐化，紀錄不會。

---

## 0. 為什麼要分階段

`NPCWorkshop.jsx` 是 4,242 行、單一檔案、8 道建角步驟 ＋ 3 個主頁籤 ＋ 十餘個周邊功能
（頭像裁切、JPG 匯出、JSON 往返、ccfolia 巨集、入戰推送、主題、揭示等級、手機版）。
一次跑完＝一次超長對話，中途任何一個阻塞缺陷都會讓後面所有觀察建立在壞地基上，
而且**額度會在中途燒光，留下半份無法解讀的紀錄**。

分階段的真正理由是**讓每一階段都能獨立結案**：
每階段結束時，紀錄必須能單獨回答「這塊功能對新手 GM 友不友善、錯在哪、怎麼修」，
不需要回頭補測。

## 1. 執行規則

### 1.1 每一階段的固定流程（五步，順序不可換）

1. **開場**：先處理上一階段留下、標記為「下一階段開頭修」的缺陷（§1.4）。
2. **走一遍**：用真實瀏覽器（CDP，見 §6）按新手 GM 的實際路徑操作，**不看原始碼**先走一遍。
   ——這一步的價值就在「不知道實作」；先讀程式碼會讓你自動繞過缺陷。
3. **對照**：只在這一步才打開原始碼，確認「我以為的預期」與「程式實際做的」差在哪。
4. **記錄**：把每個檢查點寫進 §7 對應階段，缺陷進 §4 登記表。
5. **收尾**：跑 `npm run test:npcworkshop && npm run test:npcworkshopui && npm run build`，
   確認這一階段沒有把既有護欄弄壞（即使這一階段沒改程式碼也要跑，因為它同時是下一階段的基準）。

### 1.2 缺陷分級

| 級別 | 定義 | 例子 |
|---|---|---|
| **S1 阻斷** | 流程走不完，或資料會消失／存錯 | 存檔後重新整理內容不見；匯入 JSON 靜默失敗 |
| **S2 規則錯** | 走完了，但算出來或寫出來的東西是錯的 | 額度多算一格；相性寫進錯誤欄位；匯出文字漏段落 |
| **S3 引導** | 功能正常，但新手 GM 不知道要做什麼／做完了不知道成功 | 沒有提示「這一步要選幾個」；儲存後無回饋 |
| **S4 觀感** | 不影響完成任務 | 圖示語意不對、間距、術語不統一 |

### 1.3 新手 GM 的五類困難標籤（每個 S3 缺陷必須貼一個）

- **找不到**：入口、控件、下一步不在預期位置，或藏在下拉／摺疊裡。
- **看不懂**：術語沒有解釋、規則提示不足，得回去翻規則書才知道要填什麼。
- **不敢動**：破壞性操作（刪除、覆蓋、清空）沒有確認或無法復原。
- **不知成功**：操作後沒有任何回饋，或回饋看不出「改了什麼」。
- **救不回**：填錯後沒有退路（不能取消、不能還原、重新整理就沒了）。

### 1.4 阻塞判定與修復時機（**本計畫的核心規則**）

每個缺陷登記時必須回答一個問題：**「如果不修，下一階段測出來的東西還可信嗎？」**

| 判定 | 條件 | 處置 |
|---|---|---|
| **阻塞（進阻塞池）** | 會改變後續階段的**輸入或基準**：存檔結構、額度／數值算法、`state` 初始化與遷移、相性計算、匯出文字結構、頁籤切換、共用元件行為 | **只登記，不修。** 留到最後階段（§3 階段 11）統一修 |
| **非阻塞（就地排修）** | 只影響當下這個畫面／這一個功能，後續階段不會踩到：文案、圖示、間距、單點互動回饋、排序細節 | **寫下「錯誤 ＋ 改進方案」，下一階段開場直接修掉** |

**為什麼阻塞項不當場修**：修了會讓「已經測過的階段」的基準失效，等於前面作廢；
而且同一個根因常常被多個階段踩到（例如 `migrateNpcState` 的兩份實作，見 `docs/state.md` §6 待裁定項），
集中修一次只需重測一次。**非阻塞項當場不修則是浪費**——它不會再被踩到，留著只會忘記。

**阻塞池的唯一出口**：階段 11。修完必須跑全量回歸（`npm test` ＋ `npm run build`），
並回頭把受影響階段的紀錄標上「已於階段 11 修正，重測通過」。

### 1.5 修完的定義

「修好」＝ ①改了程式碼 ②記錄裡寫了「為什麼這樣修」 ③對應階段重跑該檢查點通過
④若該缺陷值得防止復發，補一條護欄進 `tests/`（依 `AGENTS.md` §1：新護欄必須做一次刻意破壞驗證）。

只會得到「看起來對」的假陽性。

## 4. 測試通道與工具

### 4.1 為什麼不用 SSR 測試取代

`tests/npcWorkshopUi.test.mjs` 用 `react-dom/server` 渲染，**不執行事件**（`AGENTS.md` §1 已警告）。
它能保證「畫面渲染得出來」，但「點下去會怎樣」完全測不到。
GM 實測的價值就在事件鏈：點錯、連點、填錯、來回切換、重新整理。

### 4.2 工具

| 工具 | 路徑 | 用途 |
|---|---|---|
| CDP 驅動器 | `scripts/gm/cdp.mjs` | 無外部依賴（Node 24 內建 `WebSocket`）驅動 Chrome headless：導航、真實滑鼠點擊、輸入、截圖、取 DOM 文字 |
| GM 語意層 | `scripts/gm/lib.mjs` | `openWorkshop`／`gotoStep`／`snap`／`check`／`report`，把「操作」變成「一句可讀的斷言」 |
| 階段腳本 | `scripts/gm/stageN.mjs` | 每階段一支，跑完輸出檢查清單 ＋ 截圖 |
| 截圖與日誌 | `scratch/gm-test/stageN/` | 不進版控（`scratch/` 已在 `.gitignore`），但紀錄裡引用檔名 |

### 4.3 執行方式

```powershell
# 1. 起 dev server（背景）
npm run dev            # 實測落在 3001（3000 被佔用時會自動往後跳）

# 2. 跑某階段（網址用 localhost，不要用 127.0.0.1）
$env:GM_BASE='http://localhost:3001'; node scripts/gm/stage1.mjs
```

> ⚠️ **必須用 `localhost`，不能用 `127.0.0.1`**（2026-10-21 實測）：Vite 6 預設只綁 IPv6 `::1`，
> 用 `127.0.0.1` 會 `ERR_CONNECTION_REFUSED`。這個坑會讓人以為「測試通道壞了」，
> 實際上是網址寫錯。
>
> ⚠️ 這幾支腳本**不進 `npm test`**：它們需要一個跑著的 dev server 與本機 Chrome，
> 放進 CI 只會製造假失敗。它們是**人工階段的工具**，不是護欄。
> （護欄仍是 `test:npcworkshop`／`test:npcworkshopui`，那兩支不碰瀏覽器。）

> ⚠️ **視窗寬度陷阱**（`docs/handoff.md`）：`--window-size=390` 的實際視窗是 500px。
> 手機版驗證一律走 `lib.mjs` 的 `viewport(390)`（CDP `Emulation.setDeviceMetricsOverride`），不要靠啟動參數。

### 4.4 存檔夾具

手工測試不該每次從零點 8 步。夾具放在 `scratch/gm-test/fixtures/`，由
`node scripts/gm/make-fixtures.mjs` 產生（可重跑即重建）：

- `npc-a.json`：單張卡，`測試暴徒`／Lv10／精英／暴徒／`sp_beast`
- `npc-b.json`：單張卡，`測試法師`／Lv20／冠位（`championMultiplier: 2`）／法師／`sp_demon`
- `library-backup.json`：`[npc-a, npc-b]`——**刻意做成「備份全庫」的格式**，用來測「備份能不能還原」

> ⚠️ 夾具**不照 `npcEngine.createNewNPC()` 產生**：它與 `NPCWorkshop.jsx` 內手寫的 `createNewNPC`
> 不是同一份（引擎版 `name` 是「新創魔獸 / NPC」、有 `faction`／`tags`、預設物種 `sp_beast`；
> 元件版 `name` 是「未知實體」、無 `faction`／`tags`、`selectedSpeciesId: null`）。
> 照引擎版產夾具，測到的就不是玩家真的新建出來的那張卡。
> 夾具只寫「元件版一定有的欄位」，其餘交給 `migrateNpcState` 補——順便驗證遷移層。

`GM-04-03` 的修法值得單獨記，因為**第一次修的時候沒生效**。

原本在 `handleFreeModeToggleClick` 裡讀 `state.customDice` 判斷「有沒有自訂骰子」。
實測：同一次點擊中，`state.customDice` 讀到 `{}`，但畫面同一幀卻渲染著「已自定義」與「重置體質骰子」
（兩者用的是同一個 `Object.keys(...).some(...)` 條件）。加了 `window.__probeDice` 直接讀 React state，
得到 `{"MIG":"d12"}`——**閉包裡的值和真實 state 不一致**。

修法不是繼續追為什麼，而是**改成在 `useEffect` 裡讀「切換後」的 state**：

```js
const wasFreeModeRef = useRef(false);
useEffect(() => {
  const was = wasFreeModeRef.current;
  wasFreeModeRef.current = !!state.isFreeModeEnabled;
  if (was && !state.isFreeModeEnabled) { /* 這裡讀到的 customDice 才是對的 */ }
}, [state && state.isFreeModeEnabled]);
```

**教訓**：在事件處理器裡讀「即將被自己改掉的 state」，拿到的是改動前的值。
需要「改動後」的值時，用 `useEffect` 觀察變化，不要在 `onClick` 裡算。

##### ⚠️ 修好一條缺陷，弄壞了一個測試——而且壞得「全綠」

`stage8.mjs` 原本用 `innerText === '' && 內含色塊` 定位主題按鈕——**那個特徵本身就是缺陷**。

**空陣列的 `every()` 回 `true`**，所以 stage8 會繼續顯示 74/74 全綠，實際上那一整段

畫面遮了，輸出有沒有一起遮？**答案原本是「沒有」。**

| 視角 | Markdown | ccfolia `memo` | ccfolia `initiative` |
|---|---|---|---|
| 完整 | 345 字，含故事與戰術 | 含故事與戰術 | 7 |
| `10+` | **144 字**，故事與戰術都不見 | **只有** `【士兵】暴徒\n特質：不死, 遲緩` | 7（數值本來就該給） |

**紅的是測試，不是程式**。這條寫進關卡註解，避免下一輪再誤判。

#### 匯出與備份：兩種形狀，一個根因

#### 這階段踩到的四個測試方法坑（不是產品缺陷）

1. **`libCount()` 回傳物件，不是數字**（`{ shown, total }`），而且那段

#### 10.2 決定性觀測

同一份內容（只改背景故事「鐘聲在灰燼裡響了三下。」），三條存檔路徑的實測：

| 路徑 | 存檔後 `story` | 結論 |
|---|---|---|
| `Ctrl+S` | 11 字 | 正確 |
| 按「儲存」 | **0 字** | 丟資料 |
| 按「返回檔案庫」 | **0 字** | 丟資料 |

再加一組：先改名字「有名有姓」、再改故事、按「儲存」→ 名字進去了（4 字）、故事 0 字。
把順序換成「名字 → 故事 → 再改一次名字 → 儲存」→ **兩者都進去了**。

這一組「有時候成功」的觀測是破案的關鍵：它證明問題不在輸入、不在欄位、不在寫入層，
而在**按鈕持有的那份閉包是哪一次 render 的**。`state?.name` 正好在依賴陣列裡，
所以改名字會把 effect 重跑一次，順手把「上一次改名字之後的所有編輯」一起帶進去。

修法是 `stateRef`（latest-ref）：每次 commit 後同步 `stateRef.current = state`，
`handleSaveToLibrary` 讀 ref 而不是閉包。修完之後同一組探測：A/B/C/D/E 五條路徑 `story` 全部 11 字，
檔案庫預覽裡也真的看得到那段故事。

#### 10.4 這一階段最大的方法論教訓：預言機比被測物更容易壞

`probe5` 用 `document.body.innerText.includes('鐘聲')` 判斷「預覽裡有沒有那段故事」。
這條斷言**恆真**——Chrome 的 `innerText` 會把 `<input>`／`<textarea>` 的**當前值**一起回傳，
所以它讀到的是輸入框自己，不是角色卡。整個 probe 5 的結論因此作廢。

同一個病在階段 8／9 也出現過變體（`[].every()` 恆真、`innerText === ''` 定位器等於在定位缺陷本身）。
這一階段把它寫成通則：

- **要證明「有」，就找一個只可能來自目標的文字來源**（例：`.border-double` 卡面的 `textContent`，或 `localStorage` 的實際位元組）。
- **要證明「沒有」，`innerText` 一律不算數**——它分不清「沒渲染」與「渲染了但值是空的」。
- 這一階段最後選定的兩個可信來源：**React fiber 的 hook state**（`memoizedState` 鏈）與 **`localStorage` 原始字串**。
  前者回答「React 知不知道」，後者回答「寫進去了沒有」；兩者不一致的地方就是缺陷所在。

#### 11.3 新發現 `GM-11-01`：不死 b1 的「免疫換吸收」從來沒有生效過（S2，規則）

`data/speciesData.js:163` 的 b1 原文是「將對暗傷害的免疫替換為對暗傷害的吸收。」——**它沒有選項 key**，就是一句固定效果。

但 `utils/npcEngine.js` 那份 `getSpeciesAffinities` 寫的是：

```js
if (sBenefits.includes('b1') && sCfg.sp_undead_abs_choice) affs[sCfg.sp_undead_abs_choice] = 'abs';
```

`sp_undead_abs_choice` 這個 key 在 `speciesData.js`、在任何 UI、在任何存檔裡都**不存在**。於是：

- 選了 b1 → 條件永遠不成立 → 暗還是「免疫」；
- 卡面上那格**永遠不會**變成「吸收」；
- 而工坊本地那份寫的是 `affs['暗'] = 'abs'`，是對的。

兩份同時存在，所以**同一張卡在兩個畫面上會顯示不同的相性**：建構頁的相性面板用本地那份（吸收），角色卡預覽與入戰用引擎那份（免疫）。這是我在合併前逐行比對兩份實作推出來的，修完後由 `stage11-probe` A1–A5 證實三條路徑（卡面、戰鬥房間、建構頁）現在一致。

對新手 GM 的意義：他選了 b1，**看不到任何變化**，於是要嘛以為自己沒點到（`不知成功`），要嘛以為這遊戲的免疫不能改（`看不懂`）。而正確答案是「它改了，只是改在另一份程式碼沒讀的地方」。

這條缺陷在 `docs/state.md` §6 登記了九天（「`getSpeciesAffinities` 66 行 vs 70 行，行為不同」），登記的語氣是**技術債**。真正去合併的那一刻，它才變成一張 bug report。

#### 11.4 新發現 `GM-11-02`：未知定位會整頁白掉（S1，救不回）

起因是「補缺不改寫」這條原則。`tests/npcWorkshop.test.mjs` 的 G 段（`未知定位仍可遷移`）要求 `migrateNpcState` **不要**把認不得的 `role` 改寫成暴徒——只補缺失的值。我照做了，於是 `stage10` B2 立刻轉紅：

```
FAIL  B2 欄位型別全壞的卡按「編輯」不會崩
```

追下去，白頁的來源不是 `migrateNpcState`，是 `NPCWorkshop.jsx:1118` 的 `calculateStats()`：

```js
const roleData = ROLES_DATA[state.role];   // 認不得 → undefined
const lvlData = roleData.levels[state.level];  // 讀 undefined 的 levels → 整頁白掉
```

也就是說：**原本的「改寫成暴徒」不是防呆，是唯一的防護**。它把白頁擋掉了，代價是無聲改寫 GM 的資料。

兩者都要的解法是把它們分開：

1. **數值計算**用暴徒的基準值（`:1124`、`:3055`）——有數值可看 > 白頁；
2. **`state.role` 字串不動**——存檔原樣保留；
3. **步驟 1 加一條警示條**，把「這個定位不在本版資料裡」「畫面上的數值是暴徒的基準」「選任一個定位就會覆蓋」三件事講出來。

第 3 點是關鍵：轉盤只畫得出六個已知定位，所以沒有警示條的話，畫面會停在**某個**定位上，而卡片裡其實是別的字——那是比白頁更難查的謊。`stage10` B2c 現在守的就是這條（畫面必須出現「不在本版資料裡」）。

#### 11.7 方法論教訓（本階段新增）

1. **「重複實作」不是風格問題，是規則錯誤的溫床。** 兩份同名函式，一份對一份錯，而錯的那份偏偏是**匯出**用的（卡面、戰鬥房間、Markdown 都走它）。工坊裡看起來一切正常，因為工坊讀的是對的那份。
2. **登記成「技術債」的條目，合併那天會變成 bug report。** `docs/state.md` §6 只寫「行為不同」，沒寫「哪份對」。真正要動手時才被迫逐行比對，才發現其中一份是憑空的分支。
3. **守門測試會逼出另一個真 bug。** G 段要求「不要改寫定位」，拆掉 `|| '暴徒'` 之後才發現 `calculateStats` 對未知定位是白頁——一個為了保護資料而做的改動，暴露了一個為了防白頁而做的無聲改寫。
