為甚麼兩條階梯可以叫「同一張紙」。第四十輪之前，warm 與 cool 是各自挑的——冷區每一階都比暖區暗 5.8–8.0%（line 那一階差 21.52%）。後果不是「不好看」，是具體的合規缺陷：ink-2 #5c6878 在暖 panel 上是 4.78:1（過 AA），在舊冷 panel 上是 4.46:1（不過）。也就是說「把畫面換成冷區」會讓二級與三級墨一起掉出合規範圍。
修法不是把冷色調亮，是把冷區從暖區的相對亮度反推：先量暖區六階，再挑同亮度、不同色相的藍灰。最大偏差 0.726%，六階全在 1% 內，兩區都嚴格遞減。於是同一個墨在同一階的對比在兩區幾乎逐位相同（ink-3 在暖 page 6.16:1、在冷 page 6.18:1），「冷暖分層」才真的只是溫度。

03保留色：身份用掉的色相不是空房

第二十五輪立的全局規則。前四輪問「這個東西是身份嗎」，這一輪多問一句「這個色相被哪張身份表登記走了」。

規則
一個色相一旦被某張身份表的一格佔用，其他任何語意都不得再借它——包括「只是裝飾」。
為什麼
看到同一個紫，讀者學到的是「這隻怪的物種是 MONSTER」。同一頁的 MP 晶片、選中的卡片、區塊外框也是紫，那個訊號就當場失效。
怎麼擋
檔案級白名單 ＋ 硬零，而且是逐行白名單（不是「這個檔案放行」）。預算制不適用——預算允許「這裡加一個、那裡減一個」，而這裡的退化正是換一個地方偷偷用回去。
唯一例外是「替代目的地」：H23-d（書頁棕）與 H24-f（紅家族 10）用預算，因為那裡的退化模式是「拿另一個色去替代」，不是「多一個」。

成功的形狀：✓ ＋ 墨階（第二十九輪新增）

✓ 已完成／已選定
成功——不是色相，是符號＋墨階。勾勾本身承擔「完成了」的訊號，不需要顏色再說一次。
✓ 已選中
選中——墨框＋紙底，與成功的區別在於有框（border-[#3c2415]），勾勾的墨階更深（text-[#3c2415] vs text-[#6b5a4b]）。
為甚麼成功沒有顏色。紅有 ✕、警示有 GiHazardSign，成功原本只有一個顏色——emerald／green。把顏色當成功符號的問題是：同一份綠同時也在說「這個物種是 PLANT」「這個徽章是翡翠青」「這個味道是苦味」。一個色相不可能同時是身份、成功、選中、面板外殼。

解法：把成功的視覺責任從顏色移到符號——✓ 是符號，墨階是等級。這跟「警示是零色＋圖示磚」是同一條邏輯：提醒性狀態不靠色相，靠形狀和符號。主動作（可以按的東西）才用 #a63d40 accent，因為它需要被注意；成功是「已經做完了」，不該搶注意力。

05形狀與動效

圓角

只有一個值：2px（rounded）。lg／xl／md／2xl／book／ui 已從設定層刪除——寫了不會得到 3px，也不會得到 Tailwind 預設的 8px，是什麼都沒有。唯一的例外是 rounded-full（全圓不是角半徑）。第三十六輪：渲染層超標 21 → 0。

陰影

只用於真的浮起來的東西（浮層、模態、書本物件）。面板靠冷暖與色差分層，不加陰影造浮起。

動效

120–200ms，不用彈性曲線。禁裝飾性彈跳與常駐脈動：animate-bounce 0、animate-pulse 0。

「護欄綠燈」≠「行為正確」。唯一的分辨法是故意弄壞，看它會不會叫。第二十五輪跑了 13 個案例（10 紅 3 綠），第二十六輪 9 個（6 紅 3 綠），第二十七輪 7 個（7 紅），第二十八輪 7 個（7 綠）。其中一條新護欄的第一版就是假綠——「至少有一個」型斷言在收斂後的檔案裡必然為真。而護欄永遠抓不到的一類是「兩個分支不同但意思一樣」：第二十六輪有四個三元式被對映成兩個不同卻同義的值，護欄全綠，語意已經塌了，只能靠逐行讀。

第二十七輪補了兩個新教訓。（一）護欄抓得到「靜默失效」：JRPGBadge 讀 variantStyles[v] || variantStyles.gold，打錯一個字只會安靜變成金色——H24-d 把「每個用到的 variant 都登記過」變成硬性檢查。（二）破壞驗證本身也會假綠：第一版把破壞注入到檔頭註解裡，stripComments 把它一起吃掉，檔案確實壞了但護欄看到的世界裡什麼都沒發生，7 案只抓到 4 案。錨點必須落在程式碼裡。

第二十八輪補了第三個教訓，方向相反：破壞驗證也是唯一能發現護欄有洞的方法。H25 第一版掃「含『步驟 N：』的那一行」，第②案把 className 折到上一行（純排版變動），當場漏抓——破壞確實注入了，檔案確實壞了，護欄卻還是綠的。這不是腳本寫錯，是護欄的判定單位選錯了：行級判定對排版工具重排一次毫無抵抗力，而 Prettier 就是會重排。改成抓「包住『步驟 N：』的那個開標籤」才補上。
同時確立兩個形狀上的規矩：（一）集合大小的護欄要防兩個方向——border-l-4 用「恰好 3」而不是「≤ 3」，因為刪光出處也是退化；（二）硬零護欄必須配反向控制——H25／H25-a 都是「不准這樣畫」，若把警示全刪光，測試照樣全綠，所以 H25-c 斷言「那要怎麼畫」。

第二十九輪補了第四個教訓：截圖也會假綠，而且比護欄更難發現。同伴面板脫漆之後截 before/after，第一次的 before 是舊 JSX 配新 CSS——bg-green-600 被 purge 掉，兩顆「攻擊」按鈕整顆消失。這不是「新版比較好」，是假的對照。修正方法是讓腳本自己證明原始碼 = HEAD 且 CSS 不同；同時也發現 HP 條還在借翠玉色（#245c45），是看圖才看到的，不是程式碼分析。

第三十二輪補了第五個教訓，也是最根本的一個：護欄會瞎，而它不會告訴你。stripComments 把 accept="image/*" 的 /* 當成區塊註解開頭，吃掉約 50 行真實 JSX；H20「全站不得有 purple」於是看不見魔防的 text-purple-800，198 條護欄一條都沒紅。更糟的是量測工具用同一個剝註解器——「全站色相 40」是被盲點算出來的，誠實值是 41。這輪因此多了三條規矩：（一）護欄要檢查「檢查本身」——H29 用合成 fixture 證明剝註解器不吞程式碼，H29-a／b 用行號與 className 守恆逐檔守著；（二）反向控制要延伸到工具——H29-c 斷言樣本仍在，否則自檢是空轉；（三）驗證要包含負向對照——除了「弄壞後會紅」，還要證明「修好之前真的不會紅」，否則「修好了」只是說法。實測：舊剝註解器＋purple 同時存在時，H20 家族確實沒紅。

第三十三輪補了第六個教訓：護欄也有「視野」——它只看得到自己掃的那一種寫法。H24-d 的職責是抓「未登記變體靜默變金」，但它只掃 JSX 字面值，掃不到 theme.badgeVariant 的間接引用；於是 blue → cyan（一個第三十輪已刪除的鍵）在 205 條護欄下活了兩輪，安靜地變成金色、與 amber 主題撞色。補上 H30-b 之後，負向對照證明：改回 'cyan' 時 H30-b 紅、H24-d 仍不紅——缺口是量出來的，不是猜的。同輪還有個反向收穫：收斂後 H24-d 一次抓出 2 處我三次 grep 都漏掉的 gold（藏在 variant={… ? 'x' : 'gold'} 三元式裡）。護欄比人可靠。

第三十四輪補了第七個教訓，也是最容易自我欺騙的一個：殘債清單也是量出來的，而它可能只量到護欄看得到的地方。上一輪把起點寫成「珠表 11 格未登記」，開場一量是 149 個 hex／769 次——差 13 倍，因為那條護欄只掃 7 個同伴檔，其餘 138 檔從未被任何護欄看過。寫下一輪起點時必須寫清楚「這個數字是怎麼量出來的」，否則量級誤差會被當成待辦事項。
同輪還確立三件事：（一）顏色的「近」有兩個維度——只量 RGB 最大通道差會把 #f2f5f8（冷灰）判成 #fbf7ee（暖奶油）的漂移，三通道各差 10 但色相差 168°；判準改成「Δ≤12 且色相差 ≤15°」。
（二）未登記的色碼不是「待整理」，是「護欄的盲區」——它同時逃掉「必須登記」與「不准這樣配」兩張網。併回 395 處之後，藏在 hover:bg-[#8f3235] 後面的 text-white 才被 H23-e 看見（斗篷掉了）；同時也掀開三個「兩個分支不同但意思一樣」的死三元式／死 hover——正是第二十六輪說「護欄永遠抓不到」的那一類，這次是靠併成同一個字串才顯形。
（三）身份的護欄必須是注入性的，不能是計數的。破壞驗證第 ③ 案「把魔奏者的紫換成指揮官已有的紫」原本沒紅：H31-a 只問「登記過沒」（新紫也登記了）、H31-b 只數「23 個鍵還在沒」（還在）——兩條都只數「有幾個」，沒有一條看「是不是同一個」。補上 H31-d（一鍵一色）才紅。4 個破壞案例裡唯一綠的那一個，才是這輪真正的產出。

第三十五輪補了第八個教訓，也是最容易誤傷自己的一條：把字面值換成令牌時，靠那個字面值活著的護欄會一起失明。全站 814 處 text-[Npx] 改寫成 text-t10／t11 之後，三條預算護欄（text-[9px]／[10px]／[11px]）與兩條規則（9px 不得用於中文、中文段落不得低於 12px）同時綠燈——它們不是通過了，是看不到東西了。負向對照：<p className="text-t10">中文</p> 對舊判定隱形、對新判定命中。修法是改掃語法形狀（text-\[\d+px\]），再補「地板」與「反向控制」——地板防止下一個人發明 t8，反向控制防止「把微字階砍掉、全部撐到 12px」被當成修好。
同輪還有第二個假綠，層級更低：dev server 的 Tailwind 設定是啟動時快照。config 加了 t10／t11 但沒重啟，text-t10 沒有對應 CSS，元素回退成繼承的 16px——第一次的「改後」量測因此無效。分辨方法是直接抓 dev server 的 CSS 問「有沒有 .text-t10」。截圖與量測之前，先確認伺服器端的產物是你以為的那一份。

第三十六輪補了第九個教訓，也是最貴的一句：「已夾住」不等於「已收斂」。第一輪把 xl 從 12px 夾到 3px，寫下「圓角不影響版面，設定層夾住就不會爆版，逐檔改名只是製造 diff」——這句話每個字都對，於是它活了三十五輪。但設定層留著 4 個值、9 個名字，其中 6 個名字指向 3px／4px／6px，「上限 2px」從第一天起在渲染層就不成立；而文件讀起來像「已完成」，所以沒有人再去看它。修「值」不等於修「名字」：名字還在，它就會被繼續寫進新程式碼。同輪還有一個更難發現的盲區——BANNED 裡明明有 rounded-lg/xl/2xl，但它只套用在 SHELL_FILES 上，而那份清單是 2 個檔案；全站有圓角的檔案 78 個。負向對照：在 NPCWorkshop.jsx 注入 rounded-lg，舊規則全綠、H34 紅。每次寫「全站零 X」，都要問一句：這條掃描的 for 迴圈跑幾個檔案？最後一個收穫來自破壞驗證第 ⑧ 案：反向控制 rounded-full ≥ 90（實測 98）留了 8 的餘裕，「把一個檔案的圓形全改成方角」掉到 83 剛好走過去，沒紅。反向控制不是「還有一些就好」，是「一個都不能少」——餘裕是給預算的，不是給「必須存在」的東西的。

第三十七輪補了第十個教訓，也是形狀最隱蔽的一個：有些程式碼「宣告了卻不會發生」，而它的外觀比壞掉更難察覺。三筆債、三種形狀、同一個病根。
（一）scale-98 不是「縮小 2%」——Tailwind 的階梯是 0／50／75／90／95／100／105／110／125／150，沒有 98，所以那 22 個 class 產生 0 條 CSS。它跟 class="foo" 一樣什麼都不做，但在原始碼裡看起來像一個決定。逐站點量「拿掉之後還剩什麼」：44 處 scale 是唯一回饋，其中 12 處是死值 ＋ 完全沒有其他回饋——那些按鈕按下去從第一天起就沒有反應，而沒有人回報，因為「按了沒動」很容易被歸因成「我沒按到」。
（二）「有 fallback」不等於「有防禦」。theme.accent || '#a63d40' 讀起來是保險，但 getCharacterTheme() 一定回傳完整物件，所以那 248 個 hex 一次都沒被取用；而 theme.accentSoft || subpanelBg 的左邊從來不存在、theme.buttonVariant || 'primary' 的欄位第十五輪就刪了——這兩種的右邊就是真正的值。|| 的右邊如果一次都沒被取用，它就不是保險，是第二個答案。
（三）永遠不執行的分支會變成化石。那 248 個 hex 裡有 #c9a227（v4 金）、#334155／#1e293b（冷墨）、#888888（純灰）——它們活了三十六輪，正因為從來沒被畫出來過。死碼不是無害的殘留，是一份沒有人會檢查的承諾。所以修法不是「換成對的 hex」（那只是換一顆化石），是整條右邊刪掉：欄位真的不見時畫面會空掉——空掉看得見，棕色看不見。
（四）唯一真的在用的那個回退，要換來源而不是拿掉。匯出畫布真的會拿到 null 主題，第一版把 || 一起刪就紅了。「全站零回退」這個目標本身是錯的，正確目標是「顏色只能來自命名來源」——const t = theme || getCharacterTheme(null)。有名字的 fallback 是防禦，沒有名字的 fallback 是第二個答案。
（五）護欄的視野不只在檔案清單裡，也在正則的字面裡。漸層護欄逐檔記次數，看起來比白名單精確，但它數的是 bg-gradient 這個字串：它守著 2 條，而 inline radial-gradient／repeating-linear-gradient／bg-[radial-gradient(…)] 共 10 條在牆外；walk() 又只收 .js／.jsx，index.css 從未被任何護欄掃過。「逐檔記次數」比「檔案白名單」精確，所以它更難被懷疑。反向控制：同一份 inline 漸層，舊規則完全沉默，新規則看到 6 個檔案。
（六）禁掉一個機制時，要問「那個機制原本在做什麼」，然後指定新的負責人。ZeroPowerBlock 的外框是 135° 對角的線性漸層（兩端暗、中間亮）＋ 彩色投影＋內層光暈——那是金箔框的形狀，把金色換成 accent 就躲過了「沒有金色」的字面檢查。而它有測試在守（「卡片用漸層描邊外框」）：禁令與測試各量一件事，兩邊都沒錯。判決不是「刪掉漸層、卡片變普通」，是「特別」換人承擔——四角 ❖、襯線大字、浮起徽章、進場動畫四項全留，外框改實心 3px 描邊。只寫「禁止」，那個職責會自己去找下一個機制——通常是更難發現的那一個。

第三十八輪補了第十一個教訓，也是最難自己發現的一個：「兩份一樣」比「兩份不一樣」更危險。六個身份色存在三個地方——characterThemes（accent／accentDark／accentLight）、ClockTracker（fill／stroke）、index.css 的 [data-theme]（--ink／--signal）。三份的色碼一字不差，欄位名卻不一樣——所以「同名比對」抓不到，而「一字不差」會被當成「本來就該一樣」，於是沒有人問「那為什麼要寫三次」。
（一）第三份從來沒有接上電。data-theme 全站被設定 0 次；12 個變數 × 2 組只被 .ui-panel／.ui-zone 讀，而那兩條規則的引用次數是 0。它不是「第二套主題」，是一套從來沒有連上電的顏色系統——而它差一點就接上了：它的 --ink 是 #2a3240（冷墨），body 實際是 #2c221e（暖墨）。接上去全站內文會從暖墨變冷墨，而且沒有任何護欄會紅。處置是投影不是同步：新增 src/data/identityPalette.js，兩邊都往下取——「兩邊不同」在定義上不可能發生。
（二）死宣告不會讓任何東西變紅，但它會讓別的東西變綠。tailwind.config.js 的 parchment 色盤，註解寫著「過渡期保留」，實測 15 個鍵的使用次數全部是 0（連 DEFAULT；兩次「命中」都在註解裡）。這本來只是清理債——但它讓本輪新加的 H36-a 第一版對 rgba(139, 94, 52, .6) 給出綠燈，因為 #8b5e34 在設定層還算「一個登記過的令牌」。一條新護欄寫完之後如果對「它該抓的東西」是綠的，要先懷疑的不是護欄，是它讀的那張表。
（三）「合併成一個」不是「全部變成那一色」。GM 的裁決是書頁棕與強調紅合併。117 處裡有 70 處是文字（標題、標籤、圖示），照字面全部換成紅，等於宣告「這裡可以按」——而那些標題不能按（CI33：#a63d40 只給「可以按的、被選中的」）。正確解讀是暖色相只剩一個：面 → 強調紅家族，字 → 墨階。分流不是憑感覺：focus:border-[#3c2415] 43 處 vs focus:border-[#a63d40] 5 處——慣例早就形成了，只是沒有人寫下來。
（四）沒有裁決記錄的顏色就是漂移。六狀態裡動搖與憤怒各手寫了一對 hex，翻遍檔案沒有一句解釋——它們之所以手寫，是「signal 只有四個令牌、狀態有六個」的補丁，不是設計；#c0603f 在紙上只有 3.56:1。一個顏色會活下來，往往正是因為它看起來合理。
（五）護欄的價值不是「通過幾條」，是「哪幾條是唯一會紅的」。本輪五條新護欄全部做了兩層驗證：破壞後點名失敗（8/8，sha256 位元組級還原），而且各自「只有它自己變紅」——證明它們沒被既有護欄順手擋住。反過來，我原本還想加兩條，破壞驗證直接否決：命刻「覆蓋」被「色相一對一」涵蓋（六身份六主題，鴿籠原理）；九相／四屬性的「大小與可辨」在把「土」改成「電」時會讓 4 條既有護欄同時紅。一條永遠跟別人一起紅的護欄，只是讓數字變大。

這一輪的判準，兩句話：「兩份一樣」比「兩份不一樣」更危險——不一樣會被發現，一樣會被當成理所當然。死宣告不會讓任何東西變紅，但它會讓別的東西變綠。

第三十九輪補了第十二個教訓，也是最容易自我安慰的一個：把檔案加進掃描範圍，不等於檔案受到檢查。殘債清單寫著「walkSrc 只收 .js／.jsx」，照著修之後——239/239 依然全綠，零新增。那個全綠不是好消息，是證據：walkSrc 收 146 檔、加上 .css 收 147 檔，差的那 1 檔從來沒被掃過，但把它加進來之後一條護欄都沒有多紅。
（一）缺口不是檔案，是寫法。護欄的樣式長成 text-[13px]，而 CSS 寫的是 font-size: 13px——兩者永遠不會相遇。把禁令按寫法排成一張表，缺口就自己浮出來：任意字級只有第一種（Tailwind）被看見，圓角前兩種，而漸層從第十輪就三種全認（GRAD_TOKEN 同時認得 bg-gradient-*、bg-[…] 與裸的 linear-gradient(）。一個正確的範例擺在旁邊十輪，比沒有範例更難發現——因為它不會出錯，所以沒有人去讀它。
（二）49 處行內字級全部在同一個檔案。這一點決定了判準：散在三十個檔案裡叫漂移，集中在一個檔案裡、而那個檔案是固定畫布，叫一條沒有名字的階梯。匯出頁 1123×794 要塞進三頁角色的全部內容，10px 起跳一定溢出，而 overflow: hidden 的溢出是內容被裁掉，不是「醜一點」。它不共用同一個媒介，所以它需要自己的階梯——但它仍然需要一個階梯。只讀前半句，結論是「可以有自己的一套」；加上後半句，結論才是「把它命名」。
（三）半像素不是更精細，是雜訊。螢幕型階梯最小步距是 9.1%（10→11），而 8→8.5 是 6.3%、8.5→9 是 5.9%、9→9.5 是 5.6%——只有下限的六成。再加上 html-to-image 在不同 DPR 下捨入方向不一致，一個「層級」不該取決於對面那台機器的螢幕。一律向下取整（固定畫布上「變小」不會溢出）。收完 11 個值 → 9 階，與螢幕型階梯同數。13px（8.3%／7.7%）也在邊緣但保留——它與 12／14 構成 1px 線性階梯；界線是「整數」，不是「步距夠不夠大」，前者能寫進護欄，後者每次都要重新爭論。
（四）上一輪的修補自己留了一道傷，而且它長得跟好的時候一模一樣。--accent 全站定義 0 次，但 fallback 的值與變數原本的值完全相同，所以畫面一 px 都沒變。「宣告了卻不會發生」的前三種至少留下一個可以量的差異（數量變 0、有第二種寫法可比、行數變少）；這一種沒有差異。
（五）破壞點本身就是一個設計問題。要做到「只有它自己變紅」，H37-a 的破壞點必須放在別的檔案（H37 只讀匯出頁），H37-b 的破壞值必須挑整數 17px 而不是 8.5px（否則 H37-a 也會紅）。破壞驗證不只要「它紅了」，還要「只有它紅」。

第四十輪補了第十三個教訓，也是最容易用「改文件」逃掉的一個：當裁定與教義衝突，先問教義在講什麼，不要先改教義。GM 裁定「做冷區」，而設計文件第一句寫著「紙只有一種」——要建的東西被自己的文件明文否決。最便宜的走法是把那行字改掉，改一行比改 79 處程式碼便宜得多；但那不是修，是把量尺折彎去合尺寸。
（一）答案在亮度，不在色相。一張紙的結構是六階亮度，暖與冷是照在它上面的光。只要兩區同階等亮，紙就還是同一張紙——「紙只有一種」升級成「紙只有一種，光有兩種」，不是推翻它，是補上它沒講完的半句。這句話之所以不是文字遊戲，是因為它可以寫成一條可量測的條件（每階 ≤1%），而可量測的條件可以被護欄守住。
（二）舊的兩條階梯不是「兩區」，是兩次各自挑色。冷區每一階都比暖區暗 5.8–8.0%（line 差 21.52%），於是 ink-2 在暖 panel 是 4.78、在舊冷 panel 是 4.46。「把畫面換成冷區」會讓二級墨掉出 AA——而它活了三十九輪沒被發現，因為冷區只被用 3 次，而那 3 次是進度條底色，上面不放字。用得不夠多、所以錯得不明顯的設計，比明顯錯掉的更難發現：它每一次出現都剛好避開了會出事的用法。
（三）只對一半的名字比沒有名字更危險。#e8dcc4 文件叫 header、設定叫 line，實測 bg 122 次、border 146 次——它同時是凹下去的面與最淺的框，兩邊各半。沒有名字時人會去讀值；有名字時人會照名字用，然後拿到一半的對。改名 shade。命名不是文書工作，是量完之後才做得出來的事。
（四）4,753 對 24。暖紙 hex 4,753 處、書墨 hex 2,267 處，而 warm＋cool 令牌只有 24 處、只分佈在三個檔。令牌層不是全站的語言，它是三個檔的方言；全站真正的語言是 hex。所以「做冷區」不可能是全面遷移，只能是一個試點——當一個詞彙的使用次數是 24 而對手是 4,753，「推廣它」不是這一輪的工作，「證明它值得被推廣」才是。
（五）一次只證明一件事。只換面（bg／border／ring／divide），不換墨：溫度是「面」的語意，墨負責「這句話有多重要」、不負責「你在哪一區」。把墨也換掉，「冷暖」就變成同時換底色與字色兩件事，改壞了分不出是哪一件。
（六）護欄紅兩盞，可能是它站在上游。前面幾輪的判準是「只有 1 條紅才代表它承重」；這一輪要補一句：H38 破壞後同時 2 條紅（另一條是對比），因為把冷區某一階調深，ink-3 立刻掉到 4.5 以下。H38 不是「一條新的檢查」，它是對比失敗的預測器——它紅的時候，那個 bug 已經發生了。如果它紅的時候會拖著下游一起紅，那不是它不夠獨立，是它站在上游。
（七）能讀結構就不要讀文字。H36-c 用正則逐行讀 tailwind.config.js，而那個正則抓不到數字鍵——cool-0 與 ink 的 2／3 一直是隱形的，第三十九輪報告的「4 個死鍵」其實是「3 個 ＋ 1 個看不見的」。修法不是補一個 |(\d+)，是把整段正則刪掉改讀已經 import 進來的 twConfig。正則版本的漏洞不是寫錯，是選錯了介面。

這一輪的判準，一句話：一份會擋住自己的文件，比一份總是同意的文件有用。
第四十一輪補了第十四個教訓，也是唯一一個「護欄問錯了問題」的教訓：前面三十九條護欄讀得到那個字串，讀不到「它不存在」。CombatantCard 用 sat-hiber 表示「已行動」，註解寫著「v5 改為去飽和，這是 v5 最重要的狀態語言之一」——而全站定義 0 次。它不報錯、不影響建置、畫面照樣渲染，只是靜靜地什麼都不做；而那句註解讓它讀起來比壞掉的程式碼更可信，因為它解釋了「為什麼要這樣做」。
（一）不存在的 class 不會只是「沒有效果」，它會把原本屬於別的狀態的顏色一起帶走。cardState 是唯一提供邊框色的地方，而它是三元式——所以「已行動」不是沒有框，是沒有顏色，掉回 Tailwind preflight 的 #e5e7eb（一個不屬於冷暖兩條階梯的第三種面）；而「危機＋已行動」的紅框整個消失，血量見底的敵人只要動過一次就不再警示。GM 在戰鬥中最需要看到的東西，剛好被最常發生的狀態吃掉。
（二）最直接的修法是錯的。把 sat-hiber 定義出來，等於 filter: saturate()，而 filter 會連帶壓掉 HP 條的紅——「褪色」變成「全部灰」，包括唯一要讀的那個量。更根本的是：這個 class 之所以不存在，是因為它不該存在——卡片有兩個獨立維度（陣營、這一輪動過沒有），一個 class 只能表達一個。「已行動」的正確表達是「同一個色相往後退一階」，不是換一個濾鏡。
（三）只有這一個嗎——264 對 1。普查結果 25 種／335 處，全部是同一件事的兩半：Tailwind v4 的命名跑在 v3.4.19 上（175 處），以及 tailwindcss-animate 從未安裝（89 處，plugins: []）。它們全部是從別的地方抄來的正確答案，抄到一個版本不對的專案裡——而抄過來的東西不會報錯，所以它長到 264 處：每一次都「照著最新文件寫」，每一次都正確，每一次都什麼都沒發生。順帶一個發現：三層噪音 那條護欄的詞彙表裡有 shadow-xs，它守著一個不可能發生的陰影——護欄的詞彙也會過期，而過期的詞彙讓護欄變成「守著空氣」。
（四）量尺收緊會讓目標走出畫面。普查改了三代：v1（所有像 class 的字串）113 種／394 處，假陽性滿天飛；v2（只掃 className=）23 種／273 處——而 sat-hiber 從名單上消失了，因為它是先被指派給變數、之後才插進 className 的字串；v3（遞迴進 ${} ＋ 一層變數解析 ＋ 標記免責 ＋ 行內 <style>）才對。「精確」與「召回」不是同一件事：分類器追求精確，護欄追求召回——寧可多幾個假陽性（人工看一遍就能排除），也不要漏掉那一個真的（它會活三十九輪）。
（五）一條會自己編 CSS 的護欄。H39 現編一份 CSS（content 就是 src），再從編譯結果反解「這份 CSS 定義了哪些名字」，然後問每一個 className 裡的 token：你在這份名單上嗎？代價 ~2 秒，換來唯一一條不可能被寫死的字串騙過的檢查。H39-a（清單不得腐爛）是為了讓這份名單不能變成化石：修好一個名字，就必須把它拿掉、把預算下調。
（六）破壞點本身就是一個設計問題。H39-b 的破壞點換過一次：第一版加在書封的 shadow-e3 旁邊，三層噪音 也一起紅了——因為那一行同時有 border 與 bg-。那不是護欄不獨立，是我把兩個違規同時放進同一行。反過來，sat-hiber 那組紅 2 條是正確的（名字沒登記 ＋ 總數變多）：紅兩盞不一定是護欄不夠獨立，有時候是那件事本來就有兩個後果。
這一輪的判準，一句話：「讀起來像一個決定」不是一個決定。
