02六種語意 → 六條通道

這是整套系統的核心判準。每一個顏色決定之前，先問「這東西是身份、序、量、標記、模式，還是出處」——答案決定它能不能有顏色。

類型例子顏色怎麼給護欄形狀

03保留色：身份用掉的色相不是空房

第二十五輪立的全局規則。前四輪問「這個東西是身份嗎」，這一輪多問一句「這個色相被哪張身份表登記走了」。

規則
一個色相一旦被某張身份表的一格佔用，其他任何語意都不得再借它——包括「只是裝飾」。
為什麼
看到同一個紫，讀者學到的是「這隻怪的物種是 MONSTER」。同一頁的 MP 晶片、選中的卡片、區塊外框也是紫，那個訊號就當場失效。
怎麼擋
檔案級白名單 ＋ 硬零，而且是逐行白名單（不是「這個檔案放行」）。預算制不適用——預算允許「這裡加一個、那裡減一個」，而這裡的退化正是換一個地方偷偷用回去。
唯一例外是「替代目的地」：H23-d（書頁棕 141）與 H24-f（紅家族 10）用預算，因為那裡的退化模式是「拿另一個色去替代」，不是「多一個」。

警示為甚麼沒有顏色，以及它靠甚麼被看見。一個單一強調色的系統裡，紅只有一個名額。如果警示也拿紅，真正會弄壞資料的那顆按鈕就不再顯眼。所以界線畫在符號上：提醒用零色 ＋ 方形圖示磚，危險用 #8c2d36 ＋ ✕，主動作用 #a63d40。

第二十八輪把「警示長什麼樣」實測了一遍。三個真實情境截圖對照，讀得出來的兩個（ErrorBoundary inline、ChapterDevWarningModal）都有方形圖示磚；讀不出來的那個（Boss 技能超額）沒有磚，而且它跟「步驟 N」導言穿著同一組 class。
結論不是「零色錯了」，是零色之後形狀成了唯一通道，而形狀沒有所有權。修法：8 個步驟導言脫掉框，警示收成 WarningNote（紙底 #f9f5eb ＋ 磚底 #f4ebd9 ＋ 磚框 #d6c7ab ＋ GiHazardSign，五個部位與那兩個讀得出來的樣本逐項相同）。

警示的形狀：一種形狀，兩種語氣（第二十八輪新增）

過多的 Boss 技能

手冊建議：同一個 Boss 超過兩個 Boss 技能時要非常小心。

tone="note"——不會壞事（手冊建議、資料落差）。零色相：只有墨階。

技能列表重複

應避免給予 Boss 來自同一個技能列表的多個技能。

tone="danger"——已經出事了（違規、超額、重複）。用登記危險紅 #8c2d36。
為甚麼是圖示磚，不是左條。左條在 §CI34 之後已經被出處用掉（EditableSkill／ReadOnlySkill／咒語卡用它標「這張卡從哪來」）。警示再用左條就是「一個形狀兩個意思」。而且 border 與 border-l-4 是同一個 CSS 屬性——兩者寫在同一個 class 字串裡時，誰生效取決於 Tailwind 的產出順序（實測 .border{ 24075 < .border-l-4 24401），換一次版本就可能靜默失效。設計系統不該把巧合當承重牆。

成功的形狀：✓ ＋ 墨階（第二十九輪新增）

✓ 已完成／已選定
成功——不是色相，是符號＋墨階。勾勾本身承擔「完成了」的訊號，不需要顏色再說一次。
✓ 已選中
選中——墨框＋紙底，與成功的區別在於有框（border-[#3c2415]），勾勾的墨階更深（text-[#3c2415] vs text-[#6b5a4b]）。
為甚麼成功沒有顏色。紅有 ✕、警示有 GiHazardSign，成功原本只有一個顏色——emerald／green。把顏色當成功符號的問題是：同一份綠同時也在說「這個物種是 PLANT」「這個徽章是翡翠青」「這個味道是苦味」。一個色相不可能同時是身份、成功、選中、面板外殼。

解法：把成功的視覺責任從顏色移到符號——✓ 是符號，墨階是等級。這跟「警示是零色＋圖示磚」是同一條邏輯：提醒性狀態不靠色相，靠形狀和符號。主動作（可以按的東西）才用 #a63d40 accent，因為它需要被注意；成功是「已經做完了」，不該搶注意力。

紅的十二種用法裡，只有一種真的需要紅。危機、錯誤、刪除、HP 是危險極性——留下。冠位、職業、數量、資源磚這四種不是「紅用錯了」，是「根本不該有色相」：冠位是序（填充量）、職業是標記（符號）、數量與資源是量（墨階）。把顏色從「意思」降級成「等級」，是這一輪真正的收穫。

05形狀與動效

圓角

上限 2px（rounded-ui）。lg／xl 在設定層被夾到 3px、2xl 4px——這是還沒收完的債。

陰影

只用於真的浮起來的東西（浮層、模態、書本物件）。面板靠冷暖與色差分層，不加陰影造浮起。

動效

120–200ms，不用彈性曲線。禁裝飾性彈跳與常駐脈動：animate-bounce 0、animate-pulse 0。

「護欄綠燈」≠「行為正確」。唯一的分辨法是故意弄壞，看它會不會叫。第二十五輪跑了 13 個案例（10 紅 3 綠），第二十六輪 9 個（6 紅 3 綠），第二十七輪 7 個（7 紅），第二十八輪 7 個（7 綠）。其中一條新護欄的第一版就是假綠——「至少有一個」型斷言在收斂後的檔案裡必然為真。而護欄永遠抓不到的一類是「兩個分支不同但意思一樣」：第二十六輪有四個三元式被對映成兩個不同卻同義的值，護欄全綠，語意已經塌了，只能靠逐行讀。

第二十七輪補了兩個新教訓。（一）護欄抓得到「靜默失效」：JRPGBadge 讀 variantStyles[v] || variantStyles.gold，打錯一個字只會安靜變成金色——H24-d 把「每個用到的 variant 都登記過」變成硬性檢查。（二）破壞驗證本身也會假綠：第一版把破壞注入到檔頭註解裡，stripComments 把它一起吃掉，檔案確實壞了但護欄看到的世界裡什麼都沒發生，7 案只抓到 4 案。錨點必須落在程式碼裡。

第二十八輪補了第三個教訓，方向相反：破壞驗證也是唯一能發現護欄有洞的方法。H25 第一版掃「含『步驟 N：』的那一行」，第②案把 className 折到上一行（純排版變動），當場漏抓——破壞確實注入了，檔案確實壞了，護欄卻還是綠的。這不是腳本寫錯，是護欄的判定單位選錯了：行級判定對排版工具重排一次毫無抵抗力，而 Prettier 就是會重排。改成抓「包住『步驟 N：』的那個開標籤」才補上。
同時確立兩個形狀上的規矩：（一）集合大小的護欄要防兩個方向——border-l-4 用「恰好 3」而不是「≤ 3」，因為刪光出處也是退化；（二）硬零護欄必須配反向控制——H25／H25-a 都是「不准這樣畫」，若把警示全刪光，測試照樣全綠，所以 H25-c 斷言「那要怎麼畫」。

第二十九輪補了第四個教訓：截圖也會假綠，而且比護欄更難發現。同伴面板脫漆之後截 before/after，第一次的 before 是舊 JSX 配新 CSS——bg-green-600 被 purge 掉，兩顆「攻擊」按鈕整顆消失。這不是「新版比較好」，是假的對照。修正方法是讓腳本自己證明原始碼 = HEAD 且 CSS 不同；同時也發現 HP 條還在借翠玉色（#245c45），是看圖才看到的，不是程式碼分析。

第三十二輪補了第五個教訓，也是最根本的一個：護欄會瞎，而它不會告訴你。stripComments 把 accept="image/*" 的 /* 當成區塊註解開頭，吃掉約 50 行真實 JSX；H20「全站不得有 purple」於是看不見魔防的 text-purple-800，198 條護欄一條都沒紅。更糟的是量測工具用同一個剝註解器——「全站色相 40」是被盲點算出來的，誠實值是 41。這輪因此多了三條規矩：（一）護欄要檢查「檢查本身」——H29 用合成 fixture 證明剝註解器不吞程式碼，H29-a／b 用行號與 className 守恆逐檔守著；（二）反向控制要延伸到工具——H29-c 斷言樣本仍在，否則自檢是空轉；（三）驗證要包含負向對照——除了「弄壞後會紅」，還要證明「修好之前真的不會紅」，否則「修好了」只是說法。實測：舊剝註解器＋purple 同時存在時，H20 家族確實沒紅。

第三十三輪補了第六個教訓：護欄也有「視野」——它只看得到自己掃的那一種寫法。H24-d 的職責是抓「未登記變體靜默變金」，但它只掃 JSX 字面值，掃不到 theme.badgeVariant 的間接引用；於是 blue → cyan（一個第三十輪已刪除的鍵）在 205 條護欄下活了兩輪，安靜地變成金色、與 amber 主題撞色。補上 H30-b 之後，負向對照證明：改回 'cyan' 時 H30-b 紅、H24-d 仍不紅——缺口是量出來的，不是猜的。同輪還有個反向收穫：收斂後 H24-d 一次抓出 2 處我三次 grep 都漏掉的 gold（藏在 variant={… ? 'x' : 'gold'} 三元式裡）。護欄比人可靠。

第三十四輪補了第七個教訓，也是最容易自我欺騙的一個：殘債清單也是量出來的，而它可能只量到護欄看得到的地方。上一輪把起點寫成「珠表 11 格未登記」，開場一量是 149 個 hex／769 次——差 13 倍，因為那條護欄只掃 7 個同伴檔，其餘 138 檔從未被任何護欄看過。寫下一輪起點時必須寫清楚「這個數字是怎麼量出來的」，否則量級誤差會被當成待辦事項。
同輪還確立三件事：（一）顏色的「近」有兩個維度——只量 RGB 最大通道差會把 #f2f5f8（冷灰）判成 #fbf7ee（暖奶油）的漂移，三通道各差 10 但色相差 168°；判準改成「Δ≤12 且色相差 ≤15°」。
（二）未登記的色碼不是「待整理」，是「護欄的盲區」——它同時逃掉「必須登記」與「不准這樣配」兩張網。併回 395 處之後，藏在 hover:bg-[#8f3235] 後面的 text-white 才被 H23-e 看見（斗篷掉了）；同時也掀開三個「兩個分支不同但意思一樣」的死三元式／死 hover——正是第二十六輪說「護欄永遠抓不到」的那一類，這次是靠併成同一個字串才顯形。
（三）身份的護欄必須是注入性的，不能是計數的。破壞驗證第 ③ 案「把魔奏者的紫換成指揮官已有的紫」原本沒紅：H31-a 只問「登記過沒」（新紫也登記了）、H31-b 只數「23 個鍵還在沒」（還在）——兩條都只數「有幾個」，沒有一條看「是不是同一個」。補上 H31-d（一鍵一色）才紅。4 個破壞案例裡唯一綠的那一個，才是這輪真正的產出。

第三十五輪補了第八個教訓，也是最容易誤傷自己的一條：把字面值換成令牌時，靠那個字面值活著的護欄會一起失明。全站 814 處 text-[Npx] 改寫成 text-t10／t11 之後，三條預算護欄（text-[9px]／[10px]／[11px]）與兩條規則（9px 不得用於中文、中文段落不得低於 12px）同時綠燈——它們不是通過了，是看不到東西了。負向對照：<p className="text-t10">中文</p> 對舊判定隱形、對新判定命中。修法是改掃語法形狀（text-\[\d+px\]），再補「地板」與「反向控制」——地板防止下一個人發明 t8，反向控制防止「把微字階砍掉、全部撐到 12px」被當成修好。
同輪還有第二個假綠，層級更低：dev server 的 Tailwind 設定是啟動時快照。config 加了 t10／t11 但沒重啟，text-t10 沒有對應 CSS，元素回退成繼承的 16px——第一次的「改後」量測因此無效。分辨方法是直接抓 dev server 的 CSS 問「有沒有 .text-t10」。截圖與量測之前，先確認伺服器端的產物是你以為的那一份。
